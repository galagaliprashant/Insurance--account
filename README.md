# Protection Passport

> "Know what protects you." — a Personal Protection Intelligence Platform for
> Indian households, per `docs/PRD.md`.

Protection Passport consolidates evidence of life, health, accident,
disability, employer/group, bank-linked, card-linked and government/social
protection into one understandable household view — the **Protection
Graph**: person → source → benefit/policy → eligibility → evidence →
nominee → claim route → verification state.

This repo contains two apps:

- **`apps/web`** — the document-first MVP web app (PRD section 16): browse,
  verify and manage a household's own protection.
- **`apps/mobile`** — a claim-assist mobile app: a family member signs up,
  records a deceased relative's details, verifies **their own** identity
  (Aadhaar + PAN + OTP — a dead person can't receive an OTP, so this proves
  the claimant, not the deceased), and the app searches for the deceased's
  insurance/bank protection, raising a support ticket for anything it can't
  confirm.

Neither app connects to a real bank, card, UIDAI or Account Aggregator — see
the demo banners in each app, and "What's simulated" below.

## Repository layout

```
apps/web/        Next.js + TypeScript + Tailwind app — MVP web + the shared API
apps/mobile/      Expo (React Native) + TypeScript app — claim-assist mobile client
packages/domain/  Shared Protection Graph types + evidence/ticket logic
docs/             Product requirements
```

This is an npm workspace monorepo — run `npm install` from the **repo root**,
not inside `apps/web` or `apps/mobile`.

## Running the web app

```bash
npm install                 # from repo root
cd apps/web
cp .env.example .env        # point at a local Postgres + set a JWT_SECRET
npx prisma migrate dev      # creates the claim-assist tables
npm run dev                 # http://localhost:3000
npm test                    # unit tests
npm run build                # production build (also runs `prisma generate`)
```

## Running the mobile app

```bash
cd apps/mobile
# EXPO_PUBLIC_API_BASE_URL defaults to the deployed demo backend; override
# it to point at `npm run dev` above for local development:
EXPO_PUBLIC_API_BASE_URL=http://localhost:3000 npx expo start
```

Scan the QR code with Expo Go (iOS/Android), or press `w` for a browser
preview. The deployed backend sets permissive CORS (`src/middleware.ts`) so
the browser preview works too, not just native.

## What's implemented

**Web** — Dashboard, Protection Inventory, Family, Emergency Mode, Documents
(simulated upload), Settings, and mock API routes under `apps/web/src/app/api/*`
implementing the PRD section 8.1 contract.

**Mobile** — Sign up / log in → record a deceased person's details → verify
the claimant's Aadhaar + PAN + OTP → discovery results (matched protection,
evidence-backed) → raise a ticket for anything unconfirmed → ticket lookup
by reference number.

**Shared backend (`apps/web/src/app/api/*`)** — `auth`, `cases`, `kyc`,
`discovery`, `tickets`, backed by Postgres via Prisma
(`apps/web/prisma/schema.prisma`) — the only genuinely stateful part of this
build; everything else stays mock-data-first.

## What's simulated (read before treating this as production)

- **Aadhaar/PAN** — format-validated only (`apps/web/src/lib/kyc.ts`). No
  UIDAI or NSDL/Protean call is made. Real eKYC requires a licensed AUA/KUA.
- **OTP** — generated by our own server and returned directly in the API
  response (shown on-screen, labelled "DEMO MODE"). No SMS gateway is wired
  up.
- **Protection discovery** — matches the deceased's entered name against
  the same static demo household used by the web app
  (`apps/web/src/lib/discovery.ts`). No live bank or Account Aggregator
  call — the PRD (section 10) scopes real AA integration as a later phase.
- **Tickets** are real: persisted in Postgres with an atomic per-year
  sequence (`apps/web/src/lib/ticket-number.ts`), so a ticket number raised
  today is genuinely look-up-able later.

## Evidence & verification model

Every protection item carries one of five verification states — `VERIFIED`,
`USER_CONFIRMED`, `NEEDS_VERIFICATION`, `UNKNOWN`, `NOT_DETECTED` — per PRD
section 6. A transaction, card name or keyword is evidence of a
*possibility*, never automatic proof of coverage. See
`packages/domain/src/protection-logic.ts` and `ticket-logic.ts` (and their
tests in `apps/web/src/lib/__tests__/`) — a protection type only counts as
"found" for ticket-prompting purposes if some real finding backs it;
`UNKNOWN`/`NOT_DETECTED` still prompts a ticket.

All data in this build is fictional demo data.
